# HANDOFF.md 格式规范

`HANDOFF.md` 是交接包的核心。读者是**对本项目零背景的接手模型**。写它的唯一标准：读完 + 核对 git 现状后，接手模型不需要再问交接文档本可回答的问题。

写作总原则：

1. **具体压倒概括**：写 `src/auth/login.ts:42`，不写"认证模块"。
2. **可执行压倒描述性**：任务条目动词开头，接手模型读完就能动手。
3. **决策必须带 why**：没有理由的决策会在交接后被推翻，返工成本最高。
4. **短**：整篇目标 <400 行。大体积证据进 `attachments/`，正文只留指针。
5. **环境需求必须可检测**：7.1 清单每条带幂等只读检测命令；**禁止记录任何密钥/token/密码的值**（文档可能随 git 入库）。

## 设备指纹算法（打包与接收两侧必须一致）

```bash
fid_input="$(hostname)|$(whoami)|$(uname -s)|$(uname -m)"   # 不读 /etc 等外部文件，沙箱可用
if command -v sha256sum >/dev/null 2>&1; then
  fid=$(printf '%s' "$fid_input" | sha256sum | cut -c1-12)
elif command -v shasum >/dev/null 2>&1; then
  fid=$(printf '%s' "$fid_input" | shasum -a 256 | cut -c1-12)
else
  fid=$(printf '%s' "$fid_input" | python3 -c 'import sys,hashlib;print(hashlib.sha256(sys.stdin.buffer.read()).hexdigest()[:12])')
fi
```

- 文档只写哈希前 12 位 + OS/arch 明文（形如 `` `3f2a9c1b7d4e` · linux-x86_64 ``），**不写主机名/用户名**——文档可能随 git 入库。
- 哈希只用于判定「同一设备+同一用户」，不是安全边界；改 hostname 或换用户名会判为跨设备，后果仅是多一次环境检查；反之两台同名主机+同名用户的计算机会被判为同一设备（交给任务中的缺环境兜底）。
- 旧版交接文档无指纹行 → 按「未知」处理：有 7.1 清单则按跨设备流程检查一次，无清单则正常继续。

**需求集指纹**（接收方缓存键）：取 7.1 每行「类型|需求|必需」三列，去首尾空白、字典序排序，行间以**单个换行**连接、**末尾不加换行**，整体取 sha256 前 12 位。同一套需求在不同项目间可复用缓存。规范片段（必须逐字使用，否则缓存键不一致）：

```bash
reqid=$(sed -n '/^### 7\.1/,/^### 7\.2/p' .handoff/HANDOFF.md | grep '^|' \
  | awk -F'|' '{for(i=2;i<=6;i++) gsub(/^[ \t]+|[ \t]+$/,"",$i)} $2!="类型" && $2!~/^-+$/ {print $2"|"$3"|"$6}' | sort \
  | awk 'NR>1{printf "\n"} {printf "%s",$0}' \
  | { command -v sha256sum >/dev/null 2>&1 && sha256sum || { command -v shasum >/dev/null 2>&1 && shasum -a 256 || python3 -c 'import sys,hashlib;print(hashlib.sha256(sys.stdin.buffer.read()).hexdigest())'; }; } | cut -c1-12)
```

**本机缓存**：`~/.continue-with-x/env-cache.md`，按 `## device <指纹>` → `### req <需求集指纹>` 两级分节，记录每项结论、实际版本/路径与日期；用户提供的替代路径优先于 PATH 探测。缓存只在本机、不入库、不随同步工具走。

## 各节写作要求与正反例

### 3. 当前进度

- 每条必须落到**文件/提交/测试结果**这类可验证的锚点。
- 反例：`✅ 完成了登录功能`（接手模型不知道去哪核实）
- 正例：`✅ 登录 API 完成：src/routes/auth.ts 已实现 POST /login，13 个单测全绿（npm test）`

### 4. 任务规划

- 每条：**动词开头 + 目标文件 + 验收方式**。
- 反例：`1. [ ] 完善 UI`（无法执行）
- 正例：`1. [ ] 为登录表单增加错误提示：修改 src/components/LoginForm.tsx，接口失败时展示后端 message 字段`
- 排序原则：阻塞项 > 半成品收尾 > 新功能。

### 5. 关键决策与约束

- 反例：`采用了 JWT 方案`（为什么？换工具后被质疑就得重新讨论）
- 正例：`认证用 JWT（无状态，部署环境无共享存储）；refresh token 不落库，过期 7 天即失效——用户已确认接受此安全模型，不要改成 session 方案`

### 6. 关键文件与代码入口

- 只列接手模型**最先需要看**的 5-10 个文件，多了等于没列。
- 文件路径必须真实存在；**行号写入前必须 `grep -n` 实际核对**，凭记忆写的行号普遍漂移 2-5 行，会直接把接手模型带偏。

### 7.1 开发环境需求

- **类型枚举**：`runtime`（语言/运行时）、`pkgmgr`（包管理器）、`tool`（构建/CLI 工具）、`service`（数据库/消息队列等外部服务）、`env-var`（环境变量）、`path`（特殊路径依赖）。
- 每条必须有**幂等、只读**的检测命令——接手侧只跑清单内命令，不做全盘探测。
- `env-var` 只记名称与「是否存在」的检测命令（`test -n "${XXX:-}"`），**禁止记录值**。
- 「必需」为否的条目缺失时仅提示不阻塞；清单通常 ≤6 条，只列接手**必需**项。
- 反例：`需要 Node 环境`（接手侧无法判定装没装对）
- 正例：`` | runtime | node | `node -v` | ≥22 | 是 | ``

### 8. 风险与已知坑

- 只写**本会话中实际发生过**的（报错、误判、返工）或**用户明确提醒**的。
- 反例：`注意代码质量`（空话）
- 正例：`tests/e2e/setup.ts 依赖本地 5432 端口的 postgres，Docker 未起时 e2e 会超时 5 分钟才报错——本会话因此浪费时间，先启动 docker-compose up -d db`

## 增量交接

第 2 轮及以后的交接：

1. 读旧 HANDOFF.md，继承仍有效的背景/决策/约束（原样搬运，不重述）。
2. 已完成项从「任务规划」移入「当前进度」✅ 区。
3. 元数据表更新时间戳，`交接轮次` 标注 `第 N 轮（含第 1..N-1 轮继承要点）`。
4. **设备指纹每轮重算**（反映本轮交出方）。若与本轮不同（跨设备接力），在 7.2 保留一行注明上一台设备已验证过的关键版本，避免接手侧误判环境漂移。
5. 整体覆盖写入，不保留旧文件副本。

## 篇幅控制

| 情况 | 处理 |
|---|---|
| git diff > 200 行 | 存 `attachments/git-diff.patch`，正文第 3 节引用并概述改动要点 |
| 大文件摘录 | 截取相关区段（含行号标记）存 attachments，正文给路径 |
| 会话很长 | 只提炼与本任务直接相关的内容；闲聊/已废弃的方案丢弃 |
| 环境条目多 | 7.1 用表格不用散文，只列接手必需项；非必需项压缩为一句 |
